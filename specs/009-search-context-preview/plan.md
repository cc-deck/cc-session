# Implementation Plan: Search Context Preview

**Branch**: `009-search-context-preview` | **Date**: 2026-07-03 | **Spec**: [spec.md](spec.md)
**Input**: Feature specification from `specs/009-search-context-preview/spec.md`

## Summary

Add search context preview to the session list: when content search finds matches, display a centered snippet of the matching text instead of the session's first message, with the keyword in normal color and surrounding context dimmed. Simplify the metadata filter to match only against `first_message`, removing invisible matches on `project_name` and `git_branch`.

## Implementation Phases

### Phase 1: Data model and types

Add `MatchSnippet` and `SearchResult` structs to `src/session.rs` (or `src/search.rs` to keep search-specific types local). These are pure data types with no logic.

**Files**: `src/search.rs` (add structs)

### Phase 2: Simplify metadata filter

Modify `filter_sessions` in `src/filter.rs` to match only against `first_message`. Remove `project_name` and `git_branch` from the haystack. Update tests.

**Files**: `src/filter.rs`

### Phase 3: Snippet extraction in search

Redesign `file_matches_all` to return `Option<MatchSnippet>` instead of `bool`. Add cluster scoring logic: find all keyword positions in each message, compute span width, track the best (densest) cluster across messages, extract a 300-char window centered on it. Track `has_more` by counting total match count > 1. Prefer user messages over assistant messages at equal density.

Update `deep_search_indexed` to return `Vec<SearchResult>` by pairing the snippet from `file_matches_all` with the session from the index lookup. Update `search_file_with_metadata` similarly.

**Files**: `src/search.rs`

### Phase 4: Update TUI plumbing

Change `App::content_results` from `Vec<Session>` to `Vec<SearchResult>`. Update `search_receiver` channel type. Update `display_session_from_entry` to access `search_result.session` for Content-sourced entries. Update `rebuild_display_items` to handle the new type. Add a method to look up the snippet for a display entry.

**Files**: `src/tui/mod.rs`

### Phase 5: Snippet rendering

In `render_session_list`, when rendering a Content or Both match that has a snippet, replace `session.first_message` with the snippet text. Render keyword ranges in the theme's normal text color and everything else in `theme.text_dim`. Append `+` indicator when `has_more` is true. Truncate the snippet to the available column width.

**Files**: `src/tui/view.rs`

### Phase 6: Tests and validation

Add unit tests for:
- `MatchSnippet` construction and keyword_ranges correctness
- Cluster scoring with single keyword, multiple keywords, edge cases
- `filter_sessions` matching only first_message
- Snippet centering at message boundaries (keyword at start/end)
- UTF-8 safety in snippet extraction
- `has_more` flag accuracy

**Files**: `src/search.rs` (inline tests), `src/filter.rs` (inline tests)

## Risk Assessment

| Risk | Mitigation |
|------|-----------|
| Snippet extraction slows search | 300-char window extraction is O(1) per message, negligible vs. JSON parsing |
| UTF-8 boundary panics in snippet slicing | Use `is_char_boundary` for all slicing (existing pattern in codebase) |
| Metadata filter simplification breaks user workflows | Grouped view provides project-level filtering; breaking change documented in spec |
| Cluster scoring complexity for many keywords | Cap at the number of keywords the user typed (typically 2-3); linear scan per message |
